# Input reconciliation: Attio API docs

This file reconciles every Attio REST endpoint, URL, and auth mechanism the PRD body and addendum rely on against what `docs.attio.com` publicly documents (verified 2026-06-04 via WebFetch). The goal is to surface inaccuracies, undocumented assumptions, and gaps before build kickoff so they're not discovered mid-implementation.

## OAuth verification

Checking addendum §C.1 + §C.3 against `/docs/oauth/authorize` and `/docs/oauth/token`:

- **"Confidential-client-only flow"** — confirmed. The OAuth tutorial documents only a server-side flow with `client_secret` held by a backend. No PKCE flow, no loopback-redirect flow, no SPA/desktop flow is documented anywhere on `docs.attio.com` (verified via the canonical authorize page, token page, and the connect-an-app tutorial).
- **"`client_secret` required, no PKCE"** — confirmed. The `/oauth/token` page lists `client_secret` as required and makes no mention of `code_verifier` / PKCE. The authorize page does not list `code_challenge` / `code_challenge_method` parameters.
- **"No refresh token, no `expires_in`"** — confirmed. Neither field appears in the documented token response schema. (Operational behavior — whether tokens actually never expire, or just lack the field — is not stated; addendum §C.3 is conservative and matches what's documented.)
- **§C.1's conclusion** that embedding `client_secret` in a public `.alfredworkflow` is incompatible with OSS distribution, and therefore V1 sidesteps OAuth entirely → **accurately reflects the documented constraints**. The relay-service plan in §C.2 is the only documented path forward, since there's no public-client flow.

One small precision worth adding to §C.3: the docs reference `build.attio.com` (not `app.attio.com`) as the location where app developers register `client_id` / `client_secret` and configure redirect URIs. The authorize endpoint host itself is not explicitly named on the page excerpt; per convention it is `https://app.attio.com/authorize` and the token endpoint is `https://app.attio.com/oauth/token`, both used as such in the addendum — but the PRD should label the developer settings host as `build.attio.com` for clarity at V2 time.

## Identity endpoint

FR-025's `[ASSUMPTION: endpoint is GET /v2/self or equivalent; confirm at build]` is now confirmed:

- **`GET /v2/self`** is the documented canonical path (categorized under the "Meta" tag in docs, sometimes referenced as `/v2/meta/identify` in older index pages — but the canonical URL is `/v2/self`).
- Response includes exactly the three values FR-025 needs to cache: `workspace_id`, `workspace_slug`, and `authorized_by_workspace_member_id` (this is the "me" workspace member ID).
- Bonus fields available for free: `workspace_name` (which FR-025 already plans to display in the "Connected to <workspace name>" toast — confirmed available), `workspace_logo_url`, `scope` (PRD could use this to detect missing-scope situations proactively rather than waiting for a 403), `exp` (PAT lifetime, useful for FR-026 token rotation UX).

The PRD can drop the ASSUMPTION tag in FR-025 and §8. Addendum §C.1's mention of "GET /v2/self or equivalent" can be tightened to just "GET /v2/self".

Side note: `GET /v2/workspace_members` (also in addendum §A) is documented and useful for FR-042's record-reference editing on assignee-shaped fields, but for resolving the **current** workspace member ID, `GET /v2/self`'s `authorized_by_workspace_member_id` is the correct primary source — no list+search needed.

## Task deep-link

FR-004's URL pattern `https://app.attio.com/{workspace_slug}/tasks?command-menu-page=task&id={task_id}`:

- **Status:** undocumented. No page on `docs.attio.com` describes this URL structure. The `command-menu-page` query parameter and the route shape look like internal app routing that could be refactored without notice.
- **Evidence basis:** the user has tested one example URL that works in their workspace (`studio-florian-marin`). That's a sample size of one, in one workspace, at one point in time.
- **PRD handling is correct.** FR-004 already specifies (a) the `[ASSUMPTION]` tag, (b) the silent fallback to the tasks list view on breakage, and (c) the PM note that a release-time CI check against a fixture workspace is a candidate V2 hardening. No change needed at PRD level. The build team should know going in: this is the riskiest deep-link in the workflow and the only one without an API-returned `web_url`.

For contrast: `web_url` IS returned on people/companies/deals records per addendum §G glossary, and used by FR-014. Those deep links are contract-stable; the task deep link is not.

## Gaps worth surfacing

These are gaps that the PRD or build team should know about before kickoff. Listed in rough order of severity.

1. **[HIGH] Task `content` may not be PATCH-able via `/v2/tasks/{task_id}`.** Addendum §H closing note says "Tasks are a separate endpoint... body is `{ content: "...", deadline_at: "...", assignee_workspace_member_id: "..." }`". The public docs explicitly state only `deadline_at`, `is_completed`, `linked_records`, and `assignees` are updatable. **`content` is not in that list.** If V1 wants to support editing task content in the F-G drill-down (and UJ-4 explicitly extends "the same flow applies to any scalar field … text (`Title`)" to tasks), this needs verification at build kickoff. If task content truly is read-only via the API, FR-040 / FR-041 must be amended to exclude task `content` from editable affordances, and the drill-down for tasks should show content as read-only with the "edit in Attio →" hint per FR-044.

2. **[MEDIUM] PATCH record value shapes in addendum §H are partially wrong against current docs.** The public docs show simpler shapes than addendum §H claims:

   - Single-select: docs say `"Option name"` (string), not `[{ "option": { "id": "..." } }]`. The wrapped-object form may also work as input but the canonical input is the bare string by option name (or option ID via a different shape). **Verify at build.**
   - Record-reference: docs say a single object `{ target_object, target_record_id }`, not the array `[{ target_object, target_record_id }]` addendum claims. Single-reference fields may not need the array wrapper.
   - Email/phone: docs show a richer shape (`email_address`, `email_domain`, `email_root_domain`, `email_local_specifier` for email; `original_phone_number`, `country_code`, `phone_number` for phone). Addendum §H's `[{ "email_address": "x@y.z" }]` is simpler than docs and may either be rejected or be auto-parsed by Attio — needs build-time verification.
   - Text: docs say bare string; addendum's `[{ "value": "new string" }]` array-wrapper alternative may or may not be accepted.
   - The build should run a one-pass curl probe against a sandbox workspace for each attribute type in §H before locking in the writers. The PRD itself already has the "Exact payload shapes must be verified against the live Attio API at build time" disclaimer at the top of §H — this gap is just sharpening it with concrete diffs.

3. **[MEDIUM] `POST /v2/notes` missing required `title` and `format` fields in PRD/addendum.** FR-016/FR-017 specify content body only; addendum §A lists only `parent_object`, `parent_record_id`, `content`. The actual API requires also `title` (plaintext, no formatting) and `format` (`plaintext` or `markdown`). Build will need to decide: (a) auto-generate a title from the first line / first N chars of content, (b) prompt the user for a title as a second input step (UX cost), or (c) always send an empty / generated title like `"Quick note from Alfred"`. This is a real UX decision the PRD glossed over. Recommend amending FR-016 / FR-017 to specify a title strategy (likely option (a): first 80 chars of content, trimmed; option (c) as fallback when content is too short). Also: `format` should default to `plaintext` to match FR-017's "no markdown rendering by the workflow" policy.

4. **[MEDIUM] Task deadline range filtering claimed by addendum §A is not a documented query parameter.** Addendum §A says `GET /v2/tasks` supports "Filter by `assignee_workspace_member_id`, `is_completed`, deadline range." The docs confirm `assignee` (not `assignee_workspace_member_id` — naming is different and the param also accepts email) and `is_completed`. They do **not** document a deadline-range query param. FR-001's "due today or undated" semantics will need to be implemented client-side: fetch all open assigned tasks, then filter by `deadline_at` in the workflow code. This is fine for normal task volumes but worth knowing — the PRD shouldn't claim server-side deadline filtering.

5. **[LOW] OAuth host clarity for V2.** Addendum §C.2 step 2 says `https://app.attio.com/authorize` and §C.2 step 3 says `https://app.attio.com/oauth/token`. The canonical docs reference `build.attio.com` as where the app developer manages `client_id` / `client_secret` / `redirect_uri` configuration, but don't explicitly state the host of the authorize/token endpoints in the pages we fetched. Worth a one-line clarification at V2 design time: which subdomain hosts user-facing OAuth, vs which hosts developer config. Not blocking V1.
