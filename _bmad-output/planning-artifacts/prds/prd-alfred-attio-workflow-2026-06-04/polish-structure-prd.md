# Structural review — prd.md

## Overall density assessment

The PRD is substantive and well-organized, but it has drifted from "tight spec" toward "narrated spec" — particularly in the FR sections, where individual requirements have absorbed rationale, fallback paths, anti-FAQ asides, and cross-references that bloat each bullet to a small paragraph. The lingering happens in three places: (1) §1 ¶3, which now footnotes its own structure ("F-G is a peer of the read surface, not a footnote") instead of just laying it out; (2) the F-G block (FR-040 through FR-051), where shared phrasing around cache-invalidation, error policy, and `attio:refresh` repeats inside multiple FRs that already point at FR-047 and FR-051; (3) §7, which spends two full preamble paragraphs ("Thesis-validation gap" + "Single instrument") explaining why metrics are weak before listing them — half of that explanation already lives implicitly in NFR-009 + V2-7. The user journeys (§4) and Glossary (§10) are tight; the FR sections and §7 are where 30–50 lines could come out without losing substance.

## Proposed cuts / shortens

- **§1 ¶3 ("This PRD scopes V1...")** — The closing sentence "a reader budgeting downstream UX or architecture work should treat F-G as a peer of the read surface, not a footnote" is meta-commentary on the doc's own structure. Cut it. The preceding sentence already establishes F-G as co-headline. Saves 1 sentence; loses nothing.

- **NG5 (the "client semantics" decomposition)** — The two-transformation walkthrough ("(a) NG1 defers all record creation... (b) NG5 maps...") is rationale that belongs in the decision log it already links to (`[[client-semantics]]`). Replace the paragraph with: "The brain dump's 'créer des nouveaux clients' resolves in V1 to 'find an existing person and update their lifecycle attribute slug' — NG1 defers creation; lifecycle is a configured attribute (FR-033), not a distinct object. See [[client-semantics]]." Saves ~4 lines.

- **FR-004** — The bracketed `[ASSUMPTION:...]` and `[NOTE FOR PM:...]` both live in §8 already. The FR should state the behavior and link out. Cut from "`[ASSUMPTION:...]`" through "candidate V2 hardening.`]`"; replace with "Tasks have no API-returned `web_url`; the workflow constructs `https://app.attio.com/{workspace_slug}/tasks?command-menu-page=task&id={task_id}` and silently degrades to the list view on contract break. See §8 and addendum §A." Saves ~6 lines, leaves §8 as the single home for the caveat.

- **FR-017** — Now carries note-format policy (`title` derivation, plaintext, whitespace/control-char handling) that overlaps with FR-016. Pull the shared rules (`format=plaintext`, control-char stripping, title-from-content-truncated-to-80) into one short paragraph above FR-016 ("Note creation, shared rules:") and leave FR-016/FR-017 with just the per-flow differences (newline handling, input mechanism). Saves ~3 lines and removes the awkward "Trailing whitespace is trimmed; embedded newlines are preserved in the multi-line path (FR-017) and stripped to a space in the single-line path (FR-016)" sentence that re-mentions both FRs from inside one of them.

- **FR-027** — The parenthetical "(technically possible, ergonomically poor)" and the rationale "Attio's PATs are workspace-scoped by design — the workflow accepts that constraint as-is rather than asking users to swap PATs by hand" is justification, not requirement. Trim to: "Multi-workspace is not supported in V1; PATs are workspace-scoped. One Alfred install binds to one workspace. Lands with V2 OAuth (§9 V2-3, V2-4). README documents the limitation."

- **FR-031** — The "Why 24h:" rationale paragraph ("attribute schemas change rarely... mitigated by `attio:refresh`") is a design log entry, not a requirement. Move to addendum or to the decision log. The FR can stop at "cached for 24h, keyed by workspace ID + object slug. Manual refresh via `attio:refresh` (FR-032)."

- **FR-046 ("No optimistic UI")** — The implementation note "implemented by re-running the drill-down script with a query argument `pending=<field_slug>` while a worker polls the API result" is engineering detail that belongs in the addendum. The FR only needs to say: drill-down does not reflect new values until server confirms; in-flight rows show a loading indicator. Saves ~2 lines.

- **§7 preamble (two bolded paragraphs)** — "Thesis-validation gap, named up front" and "Single instrument" together total ~6 lines of meta-commentary. Collapse to one short paragraph: "V1 forbids telemetry (NFR-009), so success metrics are GitHub-Issue-derived community-signal proxies — not direct thesis validation. The maintainer accepts the blind-when-quiet trade-off; V2-7 names the path to closing the gap." Saves ~5 lines.

- **§7 "Review cadence" paragraph** — Currently lists what the maintainer does ("reviews opened issues quarterly... no numeric thresholds; no automated dashboard; no alerts"). The "no X; no Y; no Z" enumeration is redundant after the preamble already established "no quantitative metric." Cut the second sentence; keep "The maintainer reviews opened issues quarterly, categorizes them by the labels above, and notes trend direction in release notes."

- **§8** — Reads more like prose than a list. The parenthetical sentence "(FR-025's identity endpoint was confirmed at reconciliation... — the assumption is dropped.)" is a finalize-process artefact; once finalize is complete, it has no reader value. Cut it.

## Proposed reorganizations

- **§1 ¶3** — Move the "F-G is the heavier of the two by FR count because every editable attribute type has its own input UX and API payload shape (addendum §H)" clause to the top of F-G itself (just before FR-040). That's where a reader budgeting work needs the warning; in §1 it forces an early concept (per-type payloads) that the reader has no context for yet.

- **FR-051 (Error copy policy)** — Currently sits at the very end of F-G as a "cross-cutting" FR, but it governs all error rendering across F-A through F-G + NFR-A. Promote it: move to a short "Cross-cutting" subsection between F-G and §6 (alongside FR-047, the other cross-cutter), so readers find it once instead of hunting at the end of F-G. Or keep both FR-047 and FR-051 where they are, but call out "(cross-cutting)" in their headers so they read as policy rather than F-G-specific.

- **NFR-006a** — Currently nested under NFR-B "Caching and rate limiting" but is about concurrency, not caching/rate-limiting. Promote to its own bullet under a renamed "NFR-B — Caching, rate limiting, and concurrency" header, or split into a small NFR-B' subsection. The current `NFR-006a` letter-suffix numbering signals "this got bolted on" — it deserves a real slot.

- **Glossary** — Place §10 before §4 (User journeys) rather than at the end. New readers hit "Attio object", "slug", "attribute", "scalar", "workspace member", "PAT", "Quick Look", "drill-down" inside the journeys without prior definitions. Glossary-up-front is standard for OSS PRDs aimed at contributors who are not domain-native (which §10's own intro states).

## Redundancy / repetition spots

- **"cache invalidation per FR-047" / "re-fetched and re-rendered" pattern** — FR-005, FR-043, FR-091-equivalents all describe the same post-mutation sequence (invalidate cache, re-fetch, re-render, notify). FR-047 already centralizes the cache rule. Refactor: replace the per-FR repetition with a single sentence like "On success, the cache-invalidation contract of FR-047 fires, the affected view re-renders, and a macOS notification confirms." FR-005 currently says "via the API and invalidates the task cache (FR-047)"; FR-043 says "cache invalidation per FR-047 fires, the record is re-fetched by ID, the drill-down re-renders, and a macOS notification confirms" — collapse these to share phrasing.

- **"the drill-down refreshes / re-renders / list re-fetches"** — Appears in FR-005 ("the to-do list re-fetches"), FR-043 ("drill-down re-renders"), UJ-1 ("the list refreshes"), UJ-4 ("re-renders the drill-down with the new value"). Pick one verb ("re-render") and use it consistently in FRs; leave UJ prose alone since it's narrative.

- **"workflow-owned error string (FR-051)" / "not raw Attio error text"** — FR-005 says "a workflow-owned error string (FR-051) — not raw Attio error text". FR-043 says "the workflow-owned error string per FR-051". FR-051 itself says "the workflow's own English/French strings (FR-037), not raw Attio API error text". The "not raw Attio error text" disclaimer appears three times. Once FR-051 is established (and perhaps promoted, per §reorg above), the per-FR clauses can just say "...failure surfaces an FR-051 error notification" without restating the policy.

- **Attribute-edit edge cases (FR-044, FR-048, FR-049, FR-050)** — All four describe a variant of "render read-only / hide the affordance / show a hint" for various failure or out-of-scope cases. FR-044 = type not in FR-040 → read-only with "edit in Attio". FR-048 = record-reference target outside the four supported objects → same affordance. FR-049 = no attribute schema → no edits at all. FR-050 = 403 on write → read-only-with-hint, session-scoped. These four could be folded into a single "Edit-affordance gating" sub-table or a short list under one FR header, with each gating reason as a bullet and the resulting rendering. Saves ~6 lines and removes the impression that V1 has four distinct degradation paths when really it has one (read-only with a contextual hint) parameterized by reason.

- **F-A, F-B repeated modifier semantics** — UJ-1, UJ-2, FR-007, FR-019 all describe the **→** drill-down contract ("opens a script filter listing... backspace returns to..."). UJ prose can stay; but FR-007's "Backspace returns to the to-do list" and FR-019's "backspace returns to the search results" are saying the same thing in slightly different words. A single sentence in F-E (rendering) — "Backspace from any drill-down returns to the originating list" — would let both FRs drop that clause.

- **"⏎ opens in Attio" pattern** — UJ-1 step 3 bullet 1, UJ-2 step 3 bullet 1, FR-004, FR-014 all state this. The pattern is universal in V1. Could become a one-line preamble for the FR section: "Across F-A and F-B, **⏎** on a result opens the record in Attio (using `web_url` where available)."

- **"up to 9 results / 9 task lines"** — UJ-1, UJ-2, FR-011 all repeat the number. FR-011's "consistent with the existing `people` implementation" is a useful anchor; UJ phrasing can drop the explicit 9 (just say "a list of results / tasks") and leave the cap to the FR.

## Stale sub-bullets after recent additions

- **FR-040** — The tasks-narrower-writable-surface clause ("Tasks have a narrower writable surface per Attio's API...") was added at reconciliation. After it landed, the leading sentence "Editable scalar attribute types on **records** (people, companies, deals)" parenthetical now does the same gating that the trailing tasks clause does. The "on records" framing is the new gate; the trailing "Tasks have a narrower writable surface..." is now arguably the canonical statement and could subsume the parenthetical. Consider rewriting FR-040 as "Editable scalar attribute types vary by object. On people/companies/deals: [list]. On tasks: only `deadline_at`, `is_completed`, single `assignee`, `linked_records` (task `content` is read-only)." — cleaner than the current two-clause sentence with the bold mid-FR.

- **FR-042 "Single record-reference" sub-bullet** — The clause "if the search returns zero results, the sub-list shows 'No <object> match <query>' and **⏎** is a no-op" duplicates FR-021's "Empty results state shows a single item naming the query". One of them can defer to the other. Since FR-021 governs F-B empty results and the record-reference sub-search is "reuses F-B's search semantics (FR-012)", FR-042 can drop the zero-results sentence as already covered by FR-021.

- **NFR-014** — Reads "README, currently a `TODO` placeholder, must be authored before V1.0.0: install steps (Alfred 5+, macOS version floor TBD at build), screenshots, keyword reference for every keyword in F-A through F-G, PAT-generation walkthrough with required scopes, troubleshooting, known limitations..., and license declaration (TBD at build, see §9)." The same "TBD at build" items (macOS floor, license) also appear in §8 ¶3 ("Build-time decisions..."). Consolidate the "TBD at build" list to §8 and have NFR-014 just say "README must cover install, screenshots, keyword reference (F-A–F-G), PAT walkthrough, troubleshooting, known limitations, and license — license and macOS floor per §8."

- **§9 V2-2** — Was extended at finalize to include "Plus destructive operations (record delete, link removal, archive)." But NG6 in §2 already lists destructive ops as a V2+ candidate. V2-2's main payload (multi-select / structured-name / structured-location / value-clearing) is distinct from delete/archive. The "Plus destructive operations" tail-clause makes V2-2 a grab-bag. Either give destructive ops their own V2-N entry or drop the tail-clause and let NG6 remain the canonical statement.

- **§9 V2-9 ("Policy for handling new Attio attribute types")** — The clause "V1's behavior on an unknown type is 'treat as non-FR-040, render read-only with edit-in-Attio affordance' (per FR-044)" restates what FR-044 already says. V2-9 only needs the forward-looking sentence ("V2 should articulate a release cadence for adding new types as Attio publishes them."); the V1-behavior recap is redundant.

## Net effect

Applying these proposals would remove roughly 25–35 lines (~10–13% of the document), mostly from the F-G block, FR-004's bracketed asides, §1 ¶3's meta-commentary, and §7's preamble. The bigger gain is in clarity than in length: shared phrasing for "mutation → invalidate → re-render → notify" and a single "edit-affordance gating" treatment would make F-G read as one coherent policy with four gates instead of four siblings, and moving the Glossary up-front would let readers parse §4 without backtracking.
