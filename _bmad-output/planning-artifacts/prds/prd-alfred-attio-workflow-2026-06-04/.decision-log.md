# Decision Log — Alfred Workflow for Attio CRM PRD

Canonical memory and audit trail. Every decision, change, and override is recorded here as the conversation unfolds.

---

## 2026-06-04

- **Intent:** Create new PRD.
- **Stakes calibration:** Public / community workflow (distributed to Attio users via GitHub Releases). PRD runs at full rigor: onboarding, doc, perceived quality, support model all count.
- **Form-factor:** Alfred workflow on macOS, built with fast-alfred (TypeScript + esbuild + semantic-release pipeline already wired).
- **Mid-stream state at PRD kickoff:** `people` keyword shipped (search by name, open in Attio / LinkedIn, recent-9 default, company name resolved with 24h cache). No companies UI, no tasks, no create operations. README + info.plist description are still placeholders.
- **UJ-1 (morning to-do) confirmed** — keyword `todo`, list of today's tasks (action / person / deal / company on one line), ENTER opens in Attio, ⌘ENTER marks complete in-place with notif feedback. Tasks "of today" = `is_completed=false` AND (`deadline_at ≤ end-of-day local` OR no deadline but assigned to me); overdue float to top in a separate "RETARD" group. Assignee = current workspace member resolved from token at onboarding.
- **UJ-2 (universal search) confirmed** — per-object keywords (`person`, `company`, `deal`, `task`), result list with ENTER → open in Attio, ⌘ENTER → open LinkedIn (person) / website (company), ⌥ENTER → write a quick note.
- **UJ-2 note input — decision:** primary path is single-line note (the Alfred query _is_ the note body), bound to ⌥ENTER. Alternative mod ⇧⌥ENTER opens a native macOS multi-line input window for longer notes. Both create an Attio Note linked to the selected record. **Why:** preserves the "fast" promise (omnibar-speed for the common case) without losing the option for richer content. **How to apply:** treat single-line as the default UX; multi-line is an escape hatch, not a duplicate path.
- **Preview-without-opening — decision:** both modes ship.
  - **⇧ (Quick Look)** renders a readonly HTML/markdown fiche of the record's key fields next to the result. Native Alfred pattern, low-friction "just glance" UX.
  - **→ (drill-down)** loads a sub-script-filter showing the record's linked records and quick-actions (open linked person/company/deal, write note, mark complete, etc.) as navigable list items; backspace returns to the parent list. Effectively turns the workflow into a mini-Attio navigator from the omnibar.
  - **Why both:** they cover orthogonal needs — Quick Look is for "I just want to see the deadline before deciding to act"; drill-down is for "I want to do the next thing from here without alt-tabbing to Attio." Florian explicitly chose both despite the extra maintenance surface.
  - **How to apply:** both shapes must be designed and documented per object (task / person / company / deal). Fields shown in Quick Look and items shown in drill-down are per-object and the PRD should enumerate them; both must degrade gracefully when an attribute is missing or the workspace has customized the object slug.
- **V1 / V2 scope split.** V1 = read + light in-place actions only (mark task complete, write quick note). All record-creation flows (new task, new company, new person/client) are deferred to V2. **Why:** Florian's call — creation is a much heavier UX surface (per-workspace custom attributes, multi-step input, conflict handling) and would delay a useful V1. **How to apply:** the V1 PRD must explicitly enumerate creation as out-of-scope and forward-reference V2 so reviewers don't flag it as a gap; the original brain dump named creation, so this is a documented exclusion, not an oversight.
- **Auth model — decision: OAuth in V1.** First-time use launches an OAuth flow in the system browser, Attio asks the user to authorize the workflow, token + refresh token stored via `alfredClient.config`. No PAT-paste fallback in the UX. **Why:** Florian's call, motivated by public-distribution UX (paste-a-token feels amateurish for a community workflow).
- **OAuth open technical nodes (must resolve before build, not before PRD freeze):**
  1. Does Attio support **PKCE**? Required because a public OSS Alfred workflow cannot safely embed a `client_secret` — anyone can extract it from the bundled JS. If PKCE is not supported, fall back to either (a) PAT for V1 + OAuth for V2, or (b) an installer-side relay that holds the secret. PRD flags this as an [OPEN].
  2. **OAuth callback transport on macOS.** Alfred has no HTTP server. Options: temporary localhost loopback server spun up during the flow (most common Alfred OAuth pattern), or custom URL scheme registered in `info.plist` (`alfred-attio-workflow://callback`). PRD picks loopback as default unless macOS sandboxing blocks it.
  3. **Multi-workspace.** If a user belongs to several Attio workspaces, OAuth must let them pick which one to bind the workflow to. Stored in config; can be re-run later.
- **"Client" semantics — decision:** not an object of its own. The brain dump's "créer des nouveaux clients" is interpreted as a `person` (optionally with a custom lifecycle attribute the workspace defines), and V1's `person` keyword already covers retrieval. No `client` keyword. **How to apply:** the PRD must note this interpretation so the brain dump phrasing doesn't re-surface as a missing feature during review.

## 2026-06-04 — Open question resolutions

- **OQ-1 — OAuth: ~~confirmed~~ then reversed after doc fetch.** Attio documents OAuth at https://docs.attio.com/rest-api/tutorials/connect-an-app-through-oauth but the documented flow is incompatible with a public OSS desktop client: no PKCE mentioned, `client_secret` mandatory in token exchange, loopback URIs discouraged for production. Embedding `client_secret` in a `.alfredworkflow` that anyone downloads = leaked credential.
- **Auth model — final decision (overrides prior OAuth-in-V1 decision):** **V1 ships PAT-paste, V2 plans OAuth via hosted relay.**

  - V1: user generates a Personal Access Token at https://app.attio.com/settings/api, pastes it into the Alfred workflow's native config textfield. The workflow reads it via `alfredClient.env.getEnv`. First-run-without-token shows a "token not configured" result that opens the setup guide.
  - V2 future: deploy a small relay service (Cloudflare Worker, Vercel function, or similar) that holds the `client_secret` and performs the token exchange on behalf of the desktop workflow. Workflow talks to the relay, never directly to Attio for OAuth. OAuth becomes the user-facing default; PAT stays as escape hatch.
  - **Why:** Florian's call. PAT is honest (no embedded secret), zero infrastructure to maintain, and ships V1 without an infra side-quest. OAuth-via-relay carries a permanent trust + hosting cost that's premature for an unproven workflow.
  - **How to apply:** revise UJ-3 (no browser flow, no workspace picker), F-C requirements (token-paste UX, not OAuth flow), and addendum §C (PAT mechanics + V2 relay sketch). Multi-workspace is not addressed in V1 — a PAT is workspace-scoped, so one install = one workspace; documented as a known limitation.

- **OQ-2 — Task deep-link: resolved.** Tasks do not have an API-returned `web_url`, but do have a constructible URL pattern: `https://app.attio.com/{workspace_slug}/tasks?command-menu-page=task&id={task_id}` (example provided: `studio-florian-marin/tasks?command-menu-page=task&id=8c910ee4-7080-4889-aa69-a5497e6cf8df`). **Why:** Florian tested this in his own workspace. **How to apply:** FR-004 must be rewritten — no fallback to the tasks list view; instead construct the deep-link from the workspace slug (obtained at onboarding) + task ID. Note in addendum: this URL shape is undocumented and may change; treat it as best-effort.

- **OQ-3 — Alfred 5 only.** V1 targets Alfred 5 minimum. **Why:** Florian's call — drops support for legacy Alfred 4 features and simplifies framework primitives. **How to apply:** declare `Alfred 5+` in README install section and `info.plist`; do not invest in compatibility shims.

- **OQ-4 — Localization V1: English + French.** Both languages ship in V1. **Why:** Florian is French and the brain dump was in French; he wants native French ergonomics in V1 rather than deferring. **How to apply:** NFR-012 must be revised — V1 ships EN + FR strings, with language detection on macOS system locale (fallback English). A config toggle to override system locale is a nice-to-have but should be present (FR-NEW). All UI strings stay centralized; no inline text in keyword scripts.

- **OQ-5 — `lifecycle_stage` / client awareness: configurable per workspace.** The workflow's `person` (and possibly `company`) result context line surfaces a workspace-configured custom attribute (typically the workspace's lifecycle/stage field) rather than hardcoding "client" detection. **Why:** Florian's call — every Attio workspace names this attribute differently, so the workflow must let the user point at the right one rather than guess. **How to apply:** add a config keyword or first-run option to pick which attribute slug to surface in context lines for each object type; default to none. Quick Look and drill-down already render whatever attribute the workspace has, this only affects the result-list context line.

- **2026-06-04 (later in session) — Auth model re-confirmed PAT V1 after second doc fetch.** Florian raised "OAuth 2 is doable" pointing at the App SDK guide. Re-fetched canonical `/oauth/authorize` and `/oauth/token` pages: `client_secret` is required, no PKCE documented, no refresh token, no expires_in. Confirmed PAT V1 / OAuth V2 with relay. **Why:** doc unambiguously confirms confidential-client-only, so PAT V1 is the only honest path without infra. **How to apply:** no PRD body changes from earlier PAT decision needed; this entry exists so the back-and-forth is traceable.

- **2026-06-04 (validation real-choice resolutions):**

  - **Datetime TZ — Auto-conversion local↔UTC.** Input parsed in macOS system timezone, converted to UTC for PATCH. Display converts UTC → system TZ. **Why:** UX-friendly for non-UTC users (Florian is in Paris); avoids the silent-wrong-deadline trap from the adversarial Critical finding. **How to apply:** add timezone behavior to FR-042 datetime row and §H matrix; centralize conversion in a small `tz.ts` helper.
  - **Drill-down depth — Single-level V1.** Opening a linked record from a drill-down opens it in Attio (no nested drill-down). The only sub-level allowed is record-reference editing (a sub-search overlay). **Why:** simpler state machine, no recursive refresh contracts, predictable cache invalidation. Multi-level drill-down moves to V2. **How to apply:** add explicit single-level statement to FR-019 and to drill-down FRs.
  - **Persona — Drop Paul/Sarah, use "the user".** All UJs reframed without named protagonists. **Why:** the personas were not shaping requirements; carrying them was theater. Honesty over decoration. **How to apply:** rewrite §3 Users + §4 UJs to remove "Paul"/"Sarah", switch to "the user" or role-neutral phrasing; remove §3 entirely if it becomes a single sentence.
  - **Success metrics — Reframe qualitative.** Replace M-1 to M-6 with honest qualitative framing: no quantitative thresholds, quarterly review of GitHub issues categorized by hand, trend direction is the signal. Explicitly name the thesis-validation gap (no telemetry means no direct measure of "collapse keystrokes"). **Why:** NFR-009 forbids telemetry, so the existing M-1 to M-6 thresholds were unmeasurable. Better to be honest than to ship vanity metrics with fake targets. **How to apply:** rewrite §7 Success Metrics, with V2-N opt-in telemetry left as an open V2 option.

He explicitly accepts the larger surface (more FRs, per-type input UX, attribute-type detection).
