## Primitives the PRD probably needs but doesn't name

- **Notification API — MISSING.** The PRD assumes macOS notifications across FR-005 ("notification confirms"), FR-016/FR-017 ("notification confirms"), FR-025 ("one-time macOS notification: 'Connected to <workspace name>'"), FR-043 ("macOS notification confirms"), and the UJ-1/UJ-3/UJ-4 narratives. **fast-alfred does NOT expose a notification primitive.** The `FastAlfred` class surface is exhaustively: `alfredInfo`, `userConfig`, `icons`, `config`, `env`, `cache`, `input`, `inputs`, `output`, `log`, `matches`, `inputMatches`, `error`. No `notify`, no `toast`, nothing under `userConfig` or `alfredInfo`. The workflow must shell out — either to `osascript -e 'display notification …'` (zero deps, native) or to `terminal-notifier` (better UX but requires bundling the binary or asking users to `brew install`). Addendum §F should call this out and pick one; otherwise every notification FR is hand-wavy.
- **Logging API — partially covered.** `alfredClient.log(text)` exists and writes to `stderr`, which Alfred captures in its debug log. NFR-009's "Logs stay local in Alfred's debug log" is therefore satisfied by `log()`. PRD doesn't name it explicitly; addendum §B should add it for completeness, especially for the FR-051 error path where errors should be logged but not surfaced raw.
- **Error rendering helper — covered.** `alfredClient.error(error)` already renders a ScriptFilter with the `error` icon and `⌘L`/`⌘C` affordances on the bad-input copy. The current `people.ts` uses it. The PRD's FR-051 ("workflow-owned error string") is compatible but not identical — FR-051 wants per-status-code messages, which require wrapping `error()` with a switch (or just calling `output()` directly with the localized FR-037 string).
- **Fuzzy match / `matches`** — FR-012 explicitly says no fuzzy match. `alfredClient.matches` is substring-only (case-insensitive, diacritic-aware via `String.prototype.normalize`). It IS appropriate for the V1 client-side path if needed (none of the F-A through F-G keywords filter client-side — they query Attio). **Not a gap** but worth noting in addendum §B that `matches` exists, is substring not fuzzy, and is deliberately unused because Attio handles filtering server-side.
- **Auto-update channel — confirmed absent.** NFR-013 already concedes "no auto-update". V2-8 schedules an update-notification UX. The framework offers nothing here — `alfredInfo.workflowVersion()` lets the workflow read its own version (good for `attio:diag` per FR-028), but there is no built-in "check GitHub Releases for newer tag" helper. V2-8 will need a small HTTP fetch + cached `lastChecked` in `alfredClient.config`. Not a gap, just confirmed: PRD's framing is honest.
- **`alfredClient.userConfig`** — exists, wraps `alfred-config` (`AlfredConfigService`). The PRD never mentions it. This is distinct from `alfredClient.config` (which is `conf`). `userConfig` reads/writes Alfred's per-workflow user-configuration values — the same surface `userconfigurationconfig` declares in `info.plist`. The PRD chooses `env.getEnv` for the PAT (correct, because the values are injected as env vars at script invocation), but `userConfig` could be useful if the workflow ever needs to programmatically write back a user-configuration default (e.g. seed the language choice from system locale). Not used by V1; flag for V2.
- **`alfredInfo.cache()` and `alfredInfo.data()`** — exist as `AlfredInfoService` methods returning Alfred's workflow-scoped cache / data directories. **NFR-011** ("Quick Look HTML files written to the cache directory") and **FR-034** ("Quick Look is rendered as an HTML file written to the workflow's cache directory") should use `alfredInfo.cache()` rather than hardcoding paths. The addendum should name this — currently it's implicit.

## Migration plausibility (addendum §F)

- **§F.1 — Rename keyword `people` → `person` in `info.plist`.** Plausible. The keyword string lives at `info.plist:64` inside an `alfred.workflow.input.scriptfilter` object. Rename is a one-line plist edit; no framework concerns.
- **§F.2 — Add ⌥⏎ and ⇧⌥⏎ mods.** Plausible. `AlfredListItem.mods` already types `cmd`, `alt`, `ctrl`, `fn` and their two-key combinations (`alt+ctrl`, etc.). The combo `shift+alt` is NOT in the typed `AVAILABLE_MODES` list — but `mods` is also typed `Partial<Record<…>>` and the underlying Alfred contract accepts `shift` as a modifier. Because `AlfredListItem` has `[key: string]: any`, an untyped `shift+alt` will pass through; a small type-narrowing cast may be needed. Flag for the engineer.
- **§F.3 — `quicklookurl` to generated HTML.** Plausible. `AlfredListItem.quicklookurl` is typed and accepts a file path. Wire-up writes HTML to `alfredInfo.cache()` and points `quicklookurl` at that absolute path.
- **§F.4 — `→` drill-down sub-script-filter.** Plausible at the framework level. Alfred's drill-down is wired in `info.plist` (a second script-filter object connected to the first via `connections`). The framework imposes no constraint. The script for the drill-down is just another `src/main/*.ts` entry under the default `productionScripts` glob.
- **§F.5 — Replace hardcoded TTLs with `alfredClient.cache`.** Plausible. `setWithTTL(key, value, { maxAge })` matches the current 10-min / 24-h constants cleanly. The current `people.ts` (lines 26–27) hardcodes `PEOPLE_TTL` and `COMPANY_TTL` without actually wiring them to a cache — the migration is real, not cosmetic.
- **§F.6 — Add `todo.ts`, `company.ts`, `deal.ts`, `task.ts`, `diag.ts`, `refresh.ts`.** Plausible. Default `productionScripts: ['src/main/*.ts']` (`BUNDLER_DEFAULTS`) picks them up automatically.
- **§F.7 — Centralize strings in `src/strings/{en,fr}.json`.** Framework-agnostic. The bundler doesn't restrict imports of JSON; esbuild handles JSON natively. The only thing to verify is that `BundlerOptions.assets` doesn't need an extra entry (default behavior bundles JSON inline at compile time, so no asset copy needed).
- **§F.8 — `src/common/tz.ts`.** Framework-agnostic, no concerns.
- **§F.9 — `src/common/cache.ts` with `invalidateRecord` / `invalidateListsContaining`.** Plausible. `CacheConfigService` exposes `delete` (inherited from `Conf`) implicitly — the `.d.ts` doesn't redeclare it but `Conf` has `delete(key)`. Verify at build that key-pattern invalidation (`invalidateListsContaining`) works against `Conf`'s flat key space (it does; `Conf.store` is a plain object you can iterate).
- **§F.10 — Three optional config fields in `info.plist`.** Plausible. The `userconfigurationconfig` array in `info.plist` already exists (confirmed at line 177). Adding three more `textfield` entries with `variable: LIFECYCLE_ATTRIBUTE_*` is a plist edit, and `alfredClient.env.getEnv(Variables.LIFECYCLE_ATTRIBUTE_PERSON, { defaultValue: '' })` reads them. No framework gap.
- **`fast-alfred pack` artifact and `semantic-release`.** Plausible per `PACK_ENTITIES`. Confirm at build: artifact filename (looks to be `<workflow-name>.alfredworkflow` based on the package.json `name`) matches `semantic-release-github`'s `assets` glob in `.releaserc`.
- **`alfredClient.alfredInfo.workflowVersion()` for `attio:diag` (FR-028).** Exists in `AlfredInfoService` (`workflowVersion(): string`). Reads `alfred_workflow_version` env var, which Alfred injects from `info.plist`'s `version` key — which `fast-alfred pack` updates before zipping. End-to-end loop is sound.

## Gaps worth surfacing

1. **No notification primitive (HIGH).** Addendum §B and FRs 005/016/017/025/043 silently assume notifications work. The framework offers nothing — the engineer must pick `osascript -e 'display notification "…" with title "…"'` (recommended: zero install, native) and add a `src/common/notify.ts` wrapper, then update §F to include it as item §F.11. Without this, every FR that says "notification confirms" is a hand-wave.

2. **`alfredClient.config` is plaintext on disk, not encrypted (MEDIUM).** Addendum §B says it's "`Conf`-backed persistent store" but doesn't flag that this is `sindresorhus/conf`, which writes JSON to `~/Library/Preferences/<bundle>.json` in cleartext. The PAT decision (kept in `env.getEnv`, not `config`) is correct, but NFR-010's "leverages Alfred's encrypted storage where supported" is misleading when applied to `config` — Alfred encrypts only `userconfigurationconfig` secure textfields, which the workflow reads via `env.getEnv`. Reword NFR-010 to clarify: secrets via `env.getEnv` only; `config` holds non-secret identity + flags.

3. **Loading-state mechanism for FR-046 (in-flight PATCH spinner) is non-obvious (MEDIUM).** FR-046 specifies "re-running the drill-down script with a query argument `pending=<field_slug>` while a worker polls the API result". fast-alfred has no built-in worker model and Alfred's own re-run / `rerun` knob on `AlfredScriptFilter` (capped 0.1–5.0s) is the only re-render hook. The engineer needs to choose between (a) `rerun` polling + a status file written by a detached child process, (b) a `nodemon`-style `node:child_process.spawn` daemon, or (c) just blocking the PATCH synchronously and accepting the dead-bar window. PRD §FR-046 implicitly bets on (a); addendum §B should call out `AlfredScriptFilter.rerun` as a leveraged primitive and pin the polling cadence.

4. **`fast-alfred pack` artifact naming is unverified (LOW).** The PRD's `semantic-release` wiring (NFR-013) attaches the artifact to a GitHub Release. The pack command's output filename pattern is not documented in `.d.ts` and isn't asserted by the PRD. Build-time check: run `fast-alfred pack --target-version 0.0.1 --no-pack` once to see what filename lands, then make the `semantic-release-github` `assets` glob match. Cheap to verify but easy to forget.

5. **`alfredInfo.cache()` and `alfredInfo.data()` not named for FR-034 / NFR-011 (LOW).** Both FR-034 ("written to the workflow's cache directory") and NFR-011 ("scrubbed on `attio:refresh`") rely on a path the workflow needs to read. `alfredInfo.cache()` returns the correct Alfred-scoped path. Addendum §B should add: `alfredClient.alfredInfo.cache()` for Quick Look HTML scratchspace and the `.last_checked` flags. Without naming it, the engineer might invent ad-hoc paths under `os.tmpdir()`.
